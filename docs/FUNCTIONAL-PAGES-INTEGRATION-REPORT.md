## Timetics and booking decision

Local Timetics 1.0.64 exposes `[timetics-meeting-list]` for multiple meetings and `[timetics-booking-form id="…"]` for one. The local fixture contains four separate `TEST LOCAL — [service]` one-to-one meetings, fictitious 15-minute durations, zero test prices, 09:00–17:00 daily dates in a bounded test availability range, Europe/Paris, no notifications and no payments. Those are disposable test parameters, **not Laure's service rules**. The list mode keeps one public route `/prendre-rendez-vous/`; the real plugin owns the date/slot/modal/booking. Its shortcode takes a `limit` but has no confirmed fixed-ID/category selection parameter: if more meetings are enabled, the latest four may replace the intended services or alter their order. Verify exactly the intended four in staging. A single service-based selection surface would be preferable if a tested installed Timetics version exposes it robustly. The [official service-based booking documentation](https://timetics.ai/docs/how-to-create-service-based-booking/) describes that concept, but this installed WordPress shortcode did not provide a confirmed four-service selector. No fragile local-ID preselection from service pages was implemented; they link to the canonical booking page.

Browser flow passed: four TEST LOCAL meetings rendered, modal opened on mobile, Europe/Paris calendar selected 2026-10-05, available slots displayed, booking form rejected missing Name/Email with associated `aria-invalid`/help IDs, and a fictitious name/email successfully created a booking with the native **This meeting is scheduled** result. Native result offers **Reschedule or Cancel**, which still needs policy and staging testing. The confirmation stays in Timetics; `/reservation-confirmee/` is prepared only and has no unverified redirect. The plugin result says an email was sent even though local notifications were disabled; this wording must be verified against actual outgoing mail or configured before public launch. The plugin UI remains partly English. The flatpickr day elements use `tabindex="-1"`; full keyboard traversal of the plugin calendar needs a dedicated staging accessibility check and, if required, a plugin issue. Local dummy staff appears as `localadmin`; real staff data must replace it.

No final duration, price, availability, cancellation, group capacity, questions or payment was inferred. Timetics stores weekly schedules, date ranges, buffers, minimum notice, capacity and custom fields; Laure must supply the actual values. The local meetings are one-to-one; group booking and reschedule/cancel outcomes were not proven in this fixture.

## SEO, consent and performance

`/faq/`, `/contact/` and `/prendre-rendez-vous/` render a single H1, self canonical and no noindex directive in local HTML. `/merci/` and `/reservation-confirmee/` render `noindex, follow`; a future `/reservation-annulee/` and Timetics meeting/archive URLs are also covered by the theme fallback plus Rank Math hooks. WordPress core sitemap fallback was tested: the three index pages are present and receipt pages are absent; Timetics appointment CPT is removed from its index. Local Rank Math 1.0.279 is active but its setup/sitemap module is unconfigured (`/sitemap_index.xml` is 404), so Rank Math metadata and its sitemap must be checked on staging. `/robots.txt` does not disallow receipt pages. There is no FAQ schema to conflict with Rank Math.

Complianz 7.5.5 is activated locally but has only activation defaults and no completed wizard/banner. Consequently banner keyboard/focus/mobile and third-party consent classification **could not be validated**; this is a staging gate. Timetics and Forminator scripts load where needed; the booking route retains Timetics `frontend.js` and `packages.js`. Timetics requests `https://js.stripe.com/v3` even with no payment configured; the isolated sandbox blocks that request (`ERR_NETWORK_ACCESS_DENIED`), while local booking still succeeds. Classify/verify this third-party load with Complianz on staging before public use; no theme-level script hack was added. Local plugin endpoints and page assets returned 200. No theme JavaScript errors or PHP errors appeared in frontend output.
